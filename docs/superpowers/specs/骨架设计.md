# AI Butler 骨架设计

## 1. 文档状态

- 设计阶段：项目骨架已确认，详细设计进行中
- 适用产品：同时支持 Web、Windows、macOS、Linux 的 AI Butler 客户端
- 技术基础：Vue 3、Vite、Vben Admin、Ant Design Vue、Electron、pnpm、Turbo

本文档只固化已经确认的架构决策。构建发布、自动更新、多窗口、深链、本地数据、错误处理和测试等内容将在后续设计中补充，不在本文中提前确定实现细节。

## 2. 产品与技术目标

### 2.1 产品形态

产品同时提供：

- 可独立部署的 Web 客户端；
- Windows、macOS、Linux 桌面客户端；
- Web 与桌面端共用账号体系、后端 API 和核心业务能力。

桌面端定位为增强型桌面客户端，而不是简单封装线上网站的薄壳。首版核心业务需要联网，不要求完整离线运行。

### 2.2 复用目标

- Web 与桌面端共用同一套 Vue 业务页面、路由、状态和 API 代码；
- 桌面端允许增加托盘、多窗口、深链、自动更新等桌面交互；
- 两端不强求使用完全相同的构建产物，但应使用同一个 Renderer 源码；
- 平台差异必须通过统一接口隔离，不能散落在业务页面中。

## 3. 已确认的总体方案

采用“单一 Renderer + 独立 Electron 壳”的架构：

1. `apps/web-antd` 是唯一的 Vue/Vben Renderer；
2. Web 构建输出部署到 Web 服务器；
3. Desktop 构建输出作为本地静态资源打包进 Electron 安装包；
4. `apps/desktop` 只负责 Electron 主进程、preload、安全桥接和桌面发布；
5. Web 与 Desktop 使用不同的平台适配器实现同一份 `platformApi` 契约；
6. 桌面端不直接加载线上 Web 页面作为主应用。

## 4. Vben 的定位

产品界面和布局以定制化设计为主，不沿用 Vben 默认视觉外壳，但继续保留 Vben 作为内部应用框架。

保留的 Vben 能力包括：

- Vben Form；
- VXE Table 及其适配层；
- 动态路由、菜单和权限；
- 标签页和偏好设置；
- Pinia 状态体系；
- 请求封装和拦截器；
- 国际化和通用组件。

需要替换或定制的部分包括：

- 主布局；
- 侧边导航和顶部区域；
- 品牌视觉；
- 页面结构与业务交互；
- Electron 窗口相关的桌面入口。

不采用在全新项目中零散安装 `@vben/*` 包的方式。上述 Vben 能力互相依赖，并依赖现有 monorepo 中的适配层和 workspace 包，将其视为孤立 UI 组件会增加依赖和升级风险。

## 5. 仓库组织

采用单一产品仓库。取消当前“外层容器仓库 + `client-web` Git 子模块”的两层组织方式，将现有 Vben monorepo 提升为产品根工程。

目标目录骨架如下：

```text
ai-butler/
├── apps/
│   ├── web-antd/
│   │   ├── src/
│   │   │   ├── platform/
│   │   │   ├── router/
│   │   │   ├── store/
│   │   │   └── views/
│   │   └── package.json
│   └── desktop/
│       ├── src/
│       │   ├── main/
│       │   │   └── services/
│       │   ├── preload/
│       │   └── shared/
│       └── package.json
├── packages/
│   ├── platform-api/
│   ├── @core/
│   ├── effects/
│   └── 其他 Vben 通用包
├── internal/
├── scripts/
├── ui-demo/
├── docs/
├── package.json
├── pnpm-workspace.yaml
└── turbo.json
```

各目录职责：

- `apps/web-antd`：共享 Renderer、定制布局和全部业务页面；
- `apps/desktop`：Electron main、preload、桌面能力和安装包构建；
- `packages/platform-api`：不依赖 Vue、Node.js 或 Electron 的纯 TypeScript 平台契约；
- `packages/@core`、`packages/effects` 及其他 Vben 包：保留现有框架能力；
- `ui-demo`：保留为视觉原型和需求参考；
- `docs`：保存架构、规格、发布和安全文档。

## 6. platformApi 平台边界

`platformApi` 是业务代码访问运行平台能力的唯一入口。

依赖方向固定为：

```text
Vue 页面 / Pinia Store / 业务服务
→ platformApi
  → Web Adapter
    → 浏览器能力或降级
  → Desktop Adapter
    → window.desktop
    → preload
    → Electron main services
```

### 6.1 契约层

`packages/platform-api` 只定义：

- 平台能力接口；
- 参数和返回值类型；
- 能力探测结果；
- 统一错误模型；
- 事件订阅与取消订阅契约。

该包不得依赖 Vue、Electron、Node.js 或具体存储实现。

### 6.2 Web Adapter

Web Adapter 负责：

- 使用标准浏览器 API 实现可用能力；
- 对桌面专属能力提供明确的“不支持”结果；
- 根据能力探测控制桌面专属入口是否显示；
- 禁止模拟不存在的高权限能力。

### 6.3 Desktop Adapter

Desktop Adapter 只调用 preload 通过 `contextBridge` 暴露的 `window.desktop` 白名单接口，不直接导入 Electron。

### 6.4 初步能力命名空间

首版 `platformApi` 按以下领域拆分：

- `runtime`：运行平台、应用版本和能力探测；
- `notification`：系统通知；
- `window`：打开、聚焦和关闭业务窗口；
- `deepLink`：接收和消费受支持的深链接；
- `updater`：检查、下载、安装更新及进度事件；
- `secureStorage`：保存少量敏感键值；
- `app`：开机启动和托盘相关偏好。

这只是已经确认的能力边界。各方法签名、状态机和错误码将在后续详细设计中确定。

## 7. Electron 安全基线

以下规则是不可绕过的架构约束：

- 开启 `contextIsolation`；
- 关闭 `nodeIntegration`；
- Renderer 不直接访问 Node.js 和 Electron；
- 不提供 `invoke(channel, payload)` 形式的通用 IPC；
- 不向 Renderer 暴露任意文件路径、SQL、Shell 命令或进程执行能力；
- 每个 IPC 通道必须单独声明；
- preload 和主进程都要校验输入；
- 主进程验证 IPC 调用来源；
- 事件订阅必须提供取消订阅函数；
- 桌面主界面使用安装包内静态资源；
- 远程页面不得获得桌面权限。

## 8. 已确认的桌面端范围

首个桌面版本需要支持：

- 系统托盘；
- 桌面通知；
- 开机启动；
- 自动更新；
- 多窗口；
- 协议唤起和深链接；
- 少量本地数据或安全存储。

运行约束：

- 核心业务要求联网；
- Web 与 Desktop 共用后端 API；
- 使用应用内账号登录并共用 Token 体系；
- 桌面页面随安装包发布，通过应用更新升级；
- Windows、macOS、Linux 同时首发。

首版最低发布目标：

- Windows x64；
- macOS x64 和 arm64；
- Linux x64 AppImage。

## 9. 明确不采用的方案

- Electron 直接以线上 Web 地址作为主应用；
- Web 与 Desktop 维护两套重复业务页面；
- Renderer 开启 Node.js；
- 业务页面直接调用 IPC；
- 将 Vben 当作单一 npm UI 组件库重新拼装；
- Web 与 Electron 分成互不协调的独立仓库；
- 首版实现完整离线业务和双向冲突同步。

## 10. 后续设计范围

后续设计按以下顺序继续：

1. Web/Desktop 开发、构建及产物组织；
2. Electron 应用启动和进程生命周期；
3. `platformApi` 具体接口、能力探测和错误模型；
4. preload 与 IPC 通道；
5. 托盘、通知和开机启动；
6. 多窗口、深链及登录态共享；
7. 本地数据与 Token 安全存储；
8. 自动更新、签名、公证和三端发布；
9. 日志、崩溃恢复和可观测性；
10. 单元测试、集成测试、桌面冒烟测试和 CI；
11. 当前 Git 子模块向单仓库结构迁移的执行方案。

每一部分经过确认后，再进入完整实现计划。
